# magicpin AI Challenge — submission

**Team:** Rahul Kumar (rahulkumar_23bt103@dtu.ac.in)

## Approach

One composer (`composer.py`) drives everything: merchant-facing and
customer-facing sends, the live `/v1/tick` loop, and `submission.jsonl`. It
tries an LLM first (temperature=0, Anthropic by default — see
`llm_client.py`) and falls back to a deterministic, per-kind heuristic
engine when no API key is set, the call fails, or the LLM's output fails
validation (taboo words, internal jargon, empty body, exact repeat). Both
paths obey the same rule set (`SYSTEM_PROMPT` in `composer.py` doubles as
the spec the heuristic engine implements in code).

**The one design choice that mattered most:** the trigger's `kind` is
treated as a *hint*, never as ground truth. A large fraction of the 100
triggers in the dataset are generator-emitted with placeholder payloads
(`{"placeholder": true}`), and a few seeded ones don't match the
merchant/customer's real state (e.g. a `customer_lapsed_soft` trigger
pointing at a customer whose real `state` is `"active"`). Rather than
parrot an unverified claim — which the judge's own anti-fabrication penalty
would catch anyway — the composer always checks `merchant.performance`,
`merchant.signals`, `customer.state`, `customer.relationship`, etc. first
and reframes around whatever is actually true and specific, calling out the
substitution in `rationale` every time. Concretely: a `perf_dip` trigger
whose real `delta_7d` shows no dip gets redirected to the merchant's
actual highest-leverage open item (expired subscription, unverified GBP,
no active offer, stale posts — in that priority order); a `chronic_refill_due`
trigger fired at a *dentist* gets reworded to "check-up" instead of
"refill"; an `ipl_match_today` trigger for a non-weeknight match gets
redirected to the category digest's own finding that weekend IPL nights
underperform for dine-in, instead of blindly pushing a match-night combo.

`/v1/reply` (`conversation_handlers.py`) is rule-based on purpose, not
LLM-based: opt-out ("stop"/"unsubscribe") is unconditional and immediate;
auto-reply is detected by phrase-matching known WhatsApp Business canned
replies plus verbatim-repeat, with one polite redirect attempt before
exiting (mirrors production Vera's own Pattern B); explicit commitment
("let's do it", "go ahead") skips straight to action mode with zero further
qualifying questions — the exact intent-handoff failure the brief calls
out; hostility gets a short de-escalation instead of an immediate hangup,
so a Phase-4-style "abuse, then an unrelated question" replay doesn't
forfeit its later turns; a short out-of-scope list (tax filing, legal
advice, etc.) gets a one-line decline + redirect back to mission.

## Tradeoffs

- **Heuristic-first, not LLM-first, in what ships here.** I don't have
  outbound access to a live LLM API in the environment I built this in, so
  everything in `submission.jsonl` was generated by the deterministic
  heuristic path (`LLM_PROVIDER=none`), not the LLM path — `build_submission.py`
  regenerates it from scratch, so nothing was hand-typed. The code is
  written so that setting `ANTHROPIC_API_KEY` (or `OPENAI_API_KEY`) before
  deploying `bot.py` switches the live bot to the LLM path with no other
  changes; I'd expect the LLM path to out-score the heuristic one on fluency
  and on trigger kinds I didn't hand-model, at the cost of per-call latency
  and cost.
- **`/v1/reply`'s NLU is regex/keyword-based, not learned.** This makes it
  fast, free, transparent, and easy to audit turn-by-turn (every rule is a
  literal pattern list at the top of `conversation_handlers.py`), but it
  will miss phrasings my pattern lists don't cover — a hostile message that
  doesn't use any of my ~10 hostility keywords falls through to the generic
  nudge path instead of de-escalating. A production version should route
  `/v1/reply` through the same LLM path as `compose()` once volume justifies
  the cost, with the rule-based checks kept only as a fast, free pre-filter
  for the unconditional cases (opt-out, exact-repeat auto-reply).
- **No true 24h WhatsApp session-window tracking.** The dataset's
  `conversation_history` gives sampled past turns, not an authoritative
  "session open until X" timestamp, so `is_first_touch` is approximated as
  "have I sent this merchant anything yet this test window" rather than a
  real 24h clock. `template_name`/`template_params` are populated on every
  tick action as a result, even though only the true first touch needs them.

## What additional context would have helped most

1. **A real peer set, not just category-wide averages.** `peer_stats` gives
   one aggregate number per category; the brief calls out social proof
   ("3 dentists in your locality did X this month") as production Vera's
   single biggest missed lever, and I can't build that message honestly
   without knowing which specific peers exist and what they actually did.
2. **An authoritative session-window / last-outbound timestamp per merchant**,
   so `is_first_touch` and template-vs-freeform selection could be exact
   instead of inferred from what I've sent this test run.
3. **A visible "already-live offer's end date"** — offers in `MerchantContext`
   have a `started` date but no expiry, so I can't build genuine
   loss-aversion urgency ("this ends Friday") without inventing a date.

## Files

| File | Purpose |
|---|---|
| `bot.py` | FastAPI server — all 5 required endpoints + optional `/v1/teardown` |
| `composer.py` | The composition engine (LLM path + heuristic fallback), shared by `bot.py` and `build_submission.py` |
| `llm_client.py` | Minimal stdlib-only Anthropic/OpenAI wrapper, temperature=0, fails soft |
| `conversation_handlers.py` | `/v1/reply` multi-turn logic (auto-reply, opt-out, hostility, intent-transition, out-of-scope, graceful exit) |
| `build_submission.py` | Regenerates `submission.jsonl` from the canonical 30 test pairs via `composer.compose()` — fully reproducible |
| `submission.jsonl` | The 30 scored compositions |
| `dataset/` | The provided seed dataset + `generate_dataset.py`, and `dataset/expanded/` (its deterministic output, incl. `test_pairs.json`) |

## Running it

```bash
pip install -r requirements.txt

# regenerate the expanded dataset + submission.jsonl (deterministic, same
# output every time):
python dataset/generate_dataset.py --seed-dir dataset --out dataset/expanded
python build_submission.py

# run the bot (heuristic mode — no key needed):
uvicorn bot:app --host 0.0.0.0 --port 8080

# or with a real LLM as the primary composer:
ANTHROPIC_API_KEY=sk-... uvicorn bot:app --host 0.0.0.0 --port 8080
```

Then deploy `bot.py` to any host that gives a public URL (Render, Fly,
Railway, an ngrok tunnel, etc. — see the testing brief §6) and submit that
URL. `judge_simulator.py` (provided in the challenge brief) can be pointed
at a running instance for a local self-test before submitting.
